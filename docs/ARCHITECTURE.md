За замовчуванням приховані: місцевість, категорія, представник, зареєстрував, номер відповіді, витрати газу, тип приєднання. ```
┌──────────────────────┐   HTTPS / JSON   ┌───────────────────────────┐  Mongoose  ┌──────────────────┐
│  client (SPA)        │ ───────────────▶ │  server (Express REST)    │ ─────────▶ │ MongoDB          │
│  React + Vite + TS   │ ◀─────────────── │  routes → controller →    │            │ (replica set —   │
│  TanStack Query, RHF │  access JWT у    │  service → model          │            │  для транзакцій) │
└──────────────────────┘  заголовку,      └───────────────────────────┘            └──────────────────┘

### 2.3 Вимога до MongoDB: replica set

Атомарна реєстрація (лічильник + заява + історія + аудит) потребує **транзакцій**, а вони в MongoDB працюють лише на replica set.
- **Розробка:** MongoDB 8, запущена як replica set з одного вузла (`--replSet rs0`), **або** безкоштовний кластер MongoDB Atlas (replica set уже є).
- **Тести:** `MongoMemoryReplSet` з `mongodb-memory-server`, встановлювати нічого не треба.
- Сервер на старті перевіряє, що підключення підтримує транзакції, і відмовляється запускатися, якщо ні.

¹ Обовʼязкове для нових заяв (Zod); у Mongoose не `required`, бо частина старих записів його не має (населений пункт — до етапу 11, місцевість — до етапу 12).

Індекси:
- `{ regYear: 1, regSeq: 1 }` **unique** — остаточний захист від дублікатів;
- `{ regYear: -1, regSeq: -1 }` покриває той самий індекс, сортування «за номером» його використовує;
- `{ regDate: -1 }`, `{ createdBy: 1, regDate: -1 }`, `{ objectType: 1, regDate: -1 }`.

Інваріант `regYear === рік(regDate)` перевіряє сервіс, а також валідатор Mongoose як другий рубіж.

## 4. Номер реєстрації

- Зберігається як `regYear` + `regSeq` (числа), а **відображається** як `` `${seq}т/${year % 100}` `` → `15т/26`.
- `parseRegNumber` приймає `15т/26`, `15т/2026`, а також латинську `t` замість `т` (типова помилка розкладки) і пробіли. `РР` перетворюється на `2000 + РР`.
- Сортування за номером виконується за числами (`regYear`, `regSeq`), а не за рядком, де `10т/26` < `9т/26`.
- Пошук за номером: `15т/26` шукає точний номер, `15` — номер 15 у будь-якому році.

## 5. Механізм нумерації

### 5.1 Чому не інші підходи

| Підхід | Проблема |
|---|---|
| Номер генерує frontend | заборонено вимогами, гонка між клієнтами |
| `count() + 1` або `max + 1` | дві паралельні реєстрації бачать однакове значення й отримують однаковий номер |
| `$inc` на лічильнику **без** транзакції | атомарний, але якщо після `$inc` створення заяви впало, номер «згорів» і з'являється пропуск |
| **`$inc` на лічильнику в транзакції + унікальний індекс** | ✅ обрано: номер видається атомарно, при помилці скасовується все разом із лічильником |

### 5.2 Автоматична реєстрація

```
session.withTransaction(async () => {
  today = поточна дата за Europe/Kyiv          ← не UTC (ризик 3 у §7)
  year  = рік(today)

  repeat:
    counter = counters.findOneAndUpdate(
      { _id: year }, { $inc: { lastSeq: 1 } },
      { upsert: true, new: true, session })      ← атомарно. Перша заява року створює лічильник
    seq = counter.lastSeq
  while applications.exists({ regYear: year, regSeq: seq }, session)
                                                 ← номер уже зайнятий ручною реєстрацією — беремо наступний

  applications.create({ regYear: year, regSeq: seq, regDate: today,
                        registrationMode: 'AUTO', createdBy: me, … }, session)
  applicationChanges.create(CREATED), auditLogs.create(APPLICATION_CREATED)
})
```

Чому це надійно при одночасній роботі:
- **Конкурентність.** Дві транзакції, що одночасно змінюють один документ лічильника, конфліктують. MongoDB перериває одну з них з помилкою `WriteConflict` (`TransientTransactionError`), і `withTransaction` **автоматично повторює** її. Повтор бачить уже збільшений лічильник і отримує наступний номер.
- **Атомарність.** Якщо впав будь-який крок, скасовується все, зокрема `$inc`. Номер не згорає.
- **Другий рубіж.** Унікальний індекс `{ regYear, regSeq }`. Навіть якщо в коді буде помилка, дубліката в базі не з'явиться.
- **Рідкісна гонка «авто + ручна» на один номер.** Наприклад, уповноважений вводить вручну `16т/26`, а автоматика саме видає 16. Одна з транзакцій отримає конфлікт: тимчасовий повториться автоматично, а помилку дубліката (`E11000`) у потоці автонумерації сервіс перехоплює й повторює операцію (до 3 разів). Ручна реєстрація в такому випадку отримає 409.
- **Новий рік.** Після 00:00 01.01 за Києвом створюється лічильник `_id: 2027` і нумерація починається з `1т/27`.

Перевірка (етап 5): інтеграційний тест на `MongoMemoryReplSet` запускає 50 паралельних реєстрацій. Очікувано — номери `1…50т/26` без дублікатів і пропусків. Окремий тест — зміна року з підміненим годинником.

### 5.3 Ручна реєстрація (заднім числом)

```
Доступ: ADMIN або canManageRegistration (перевіряється на сервері, інакше 403 + аудит)
Вхід:   regDate (будь-яка дата), regNumber (наприклад, "15т/26")

1. parseRegNumber → { year, seq }. Невірний формат → 400
2. year ≠ рік(regDate) → 400 «Номер 15т/26 не відповідає року дати реєстрації»
3. session.withTransaction:
     існує { regYear, regSeq } → 409 «Номер 15т/26 уже зайнятий (заява від 12.03.2026)»
     applications.create({ registrationMode: 'MANUAL', createdBy: me, … })
     ← createdAt = фактичний момент внесення; лічильник НЕ змінюється
     applicationChanges(CREATED) + auditLogs(APPLICATION_MANUAL_CREATED)
```

Як ручна реєстрація співіснує з лічильником:
- ручний номер **≤ lastSeq** заповнює пропуск у минулому. Автонумерація назад не повертається;
- ручний номер **> lastSeq** (у тому числі «наперед») автонумерація згодом пропустить. Дублікатів немає, лічильник не стрибає;
- номер для минулого чи іншого року працює з лічильником того року (якщо лічильника немає, його не створюємо) і на поточний рік не впливає.

### 5.4 Зміна дати або номера наявної заяви

- Хто може: власник з `canManageRegistration` або адміністратор.
- Нова пара `{ year, seq }` перевіряється на унікальність (409). Рік номера має збігатися з роком дати. Якщо змінюється рік дати, номер треба змінити теж.
- Старий номер звільняється. Автонумерація його повторно **не** видає, бо лічильник рухається лише вперед. Зайняти його можна тільки вручну.
- Записуються `applicationChanges` (old → new) і `auditLogs` (`REG_NUMBER_CHANGED` / `REG_DATE_CHANGED`).

### 5.5 Анулювання

- Статус стає `ANNULLED`, обов'язково вказується причина. Номер **лишається зайнятим**, повторно не видається.
- У реєстрі анульовані заяви видно (рядок приглушений, позначка «Анульовано»), є фільтр за статусом.
- Відновлення (`RESTORED`) — лише адміністратор.
- Анулювання вимагає діалогу підтвердження і записується в історію та аудит.

### 5.6 Видалення (етап 10)

- Лише адміністратор, будь-яка заява. Підтвердження — введенням номера заяви в діалозі.
- В одній транзакції видаляються заява та її `applicationChanges`; в `auditLogs` пишеться `APPLICATION_DELETED` з номером і датою (без даних замовника). Застаріла `version` → 409, нічого не видаляється.
- Номер стає вільним для ручного внесення; лічильник автонумерації не змінюється.
- Інші записи журналу про цю заяву лишаються; посилання з них веде на «Заяву не знайдено».

### 5.7 Сортування реєстру (етап 12)

- Номер, дата й текстові стовпчики (замовник, населений пункт, адреса, представник) сортуються базою через індекси `{поле, regYear, regSeq}`; для тексту — з `collation: { locale: 'uk' }` (і в індексі, і в запиті). Тест перевіряє `explain()`: `IXSCAN` без етапу `SORT`.
- Дата відповіді й дата ТУ (етап 17.6) сортуються індексами `{ 'processing.<дата>', regYear, regSeq }` (і з `department` попереду). Заяви без документа — у кінці за зростанням.
- Стан і тип приєднання сортуються за назвою, номери документів, витрати газу й інженер — за збереженим значенням, обидва через агрегацію (той самий свідомий виняток, що нижче).
- Тип, категорія й місцевість сортуються за **назвою** (назви — в `packages/shared/src/labels.ts`), «Зареєстрував» — за ПІБ. Таких значень у документі немає, тому це агрегація з обчисленим ключем: сортування в памʼяті бази після фільтрації. **Свідомий виняток** із правила про індекси: для внутрішнього реєстру обсяг невеликий; якщо стане повільно — денормалізувати ключі в документ.

### 5.8 Єдиний рядок пошуку (етап 16)

- Параметр `q` (до 200 символів) шукає підрядок без урахування регістру в полях замовник, представник, населений пункт, адреса й коментар — через `contains()`, тобто буквально.
- Номер читається й частково набраним: `15т` чи `15т/2` — як `15` (будь-який рік), `15т/26-` — як `15т/26`; рік враховується лише повним (2 або 4 цифри), код управління — лише після року і точно (`-1` — це код 1, а не початок `-11`).
- Якщо `q` читається як номер (`15`, `15т/26`, `15т/26-8` — `parseRegNumberSearch` у shared), до збігів додається пошук за номером: «15» знаходить і заяву № 15, і «вул. Шевченка, 15». Номер із кодом чужого чи неіснуючого управління нічого не знаходить.
- Решта фільтрів звужують результат (`q` — це `$or` усередині загального «і»). Окремих параметрів пошуку за полями (`customer`, `number`…) більше немає: їх замінив `q`.
- Клієнт: рядок «Пошук», «Управління» (адміністратор), «Період» (Будь-коли / Сьогодні / Цей тиждень / Цей місяць / Цей рік — за київським часом — або довільні дати), кнопка «Ще фільтри (N)» з рідшими фільтрами; під ними — швидкі вкладки «Усі · Мої · Анульовані» і чипи активних фільтрів з «Скинути все». Усе — в URL (`q`, `from`, `to`…).
- З етапу 17.6 рядок пошуку шукає ще й номери відповідей і чинних ТУ (`processing.documentNumbers`); скасовані документи не знаходяться.
- Пошук підрядка не може використати індекс; вибірку обмежує управління й сортування за індексом (тест `explain()` перевіряє й варіант із `q`). Для внутрішнього реєстру цього достатньо; якщо стане повільно — повнотекстовий індекс.

### 5.9 Строки опрацювання в робочих днях (етап 17.2)

- Рахує **лише сервер** (`modules/calendar/workingDays.ts`, `documentDeadline()` у `calendar.service.ts`) за поточним календарем і «сьогодні» за Києвом — у всіх користувачів однакові числа.
- Робочий день: виняток календаря, якщо він є; інакше — не субота й не неділя.
- `used` — робочі дні в проміжку (дата реєстрації; дата документа]: день реєстрації не рахується, день документа рахується. Поки документа немає — до сьогодні. Документ, датований днем реєстрації чи раніше, — 0.
- `dueDate` — N-й робочий день після реєстрації; документ, датований цим днем, вчасний. `remaining = N − used` (відʼємне — прострочено), `overdueBy = max(0, used − N)`.
- Норми: відповідь — 5, ТУ — 10 робочих днів (`RESPONSE_DEADLINE_DAYS`, `TU_DEADLINE_DAYS` у shared). Відлік завжди від дати реєстрації, зокрема для заяв, внесених вручну.
- Приклад: заява пн 02.11.2026, відповідь пт 06.11 → 4 з 5, строк — 09.11. Неробочий вівторок зсуває строк на день пізніше, робоча субота — на день раніше.
- Зміна календаря одразу змінює всі розрахунки, зокрема минулих документів (знімки не зберігаються).

### 5.10 Стан заяви, зведення й хронологія (етап 17.5)

- **Стан** виводиться з документів у силі (нескасованих): чинні ТУ → «ТУ підготовлені»; інакше остання відповідь (за датою, потім за часом внесення) з датою «Документи надійшли» → «На опрацюванні», без неї → «Відповідь надана»; документів немає → «Зареєстрована». Анульована заява показується як «Анульована» (власний `status`). Перелік — `PROCESSING_STAGES` у shared. Стан не є джерелом істини: документи й хронологія зберігаються окремо.
- **Зведення** `applications.processing` (`stage`, дата й номер останньої відповіді; дата, номер, витрати газу й тип приєднання чинних ТУ; ПІБ інженера ТУ чи останньої відповіді; `engineerIds`, `documentNumbers`) переписує `recomputeProcessing()` **у тій самій транзакції**, що й зміну документа (`changeDocuments()` у `modules/documents`). `version` і `updatedAt` заяви при цьому не змінюються. Для реєстру (етап 17.6). Наявні заяви заповнює `npm run db:migrate` (`backfillProcessing`); при розбіжності — повторний запуск.
- **`GET /applications/:id/processing`** → `{ stage, deadlines: { tracked, response, tu }, events }`. Строк відповіді — за першою нескасованою відповіддю; якщо ТУ підготовлено без відповіді — `response: null`. Строк ТУ — за чинними ТУ. Поки документа немає — до сьогодні.
- **Хронологія** (`events`): реєстрація, кожна відповідь, «Документи надійшли», кожні ТУ — за датою; події однієї дати: реєстрація → відповідь → документи → ТУ, далі за часом внесення. Скасовані документи лишаються на своєму місці з `cancelled: true`. У кожної події — робочі дні від реєстрації, норма й перевищення; у ТУ після надходження документів — ще й дні від нього.
- **`PROCESSING_START_DATE`** (необовʼязкова, `YYYY-MM-DD`, `server/.env`): заяви, зареєстровані раніше, мають `deadlinesTracked: false` — числа показуються, попереджень «прострочено» немає (рішення 28). Не задано — контролюються всі.

### 6.2 Як це забезпечується на сервері

1. **`authenticate`** перевіряє access JWT (15 хв) і **читає користувача з БД** (роль, `canManageRegistration`, `isActive`). Деактивація або зміна прав діють одразу, а не через 15 хвилин.
2. **`requireRole('ADMIN')`** на маршрутах `/users` і `/audit`.
3. **Сервіс заяв** — головна перевірка:
   - редагування й анулювання: `createdBy === me || role === ADMIN`, інакше 403 + `ACCESS_DENIED` в аудит;
   - поля `regDate` і `regNumber` у запиті приймаються лише від власника з правом або від адміністратора, інакше 403;
   - Zod-схеми зі `.strict()`: зайві поля (`createdBy`, `registrationMode`, `status`) відхиляються. Захист від підміни полів (mass assignment).
4. **Захист від NoSQL-ін'єкцій:** Zod гарантує типи (рядок не може стати `{ $gt: '' }`), `mongoose.set('sanitizeFilter', true)`, а пошукові рядки перед `$regex` екрануються.
5. Frontend ховає недоступні кнопки й поля. Це зручність, а не захист.

### 6.3 Автентифікація

_Реалізовано на етапі 4.1; рішення погоджено 2026-11-15._

- Вхід за логіном і паролем. Rate limit: 10 невдалих спроб / 15 хв на пару IP + логін. Однакове повідомлення «Невірний логін або пароль» для будь-якої причини; для неіснуючого логіна виконується фіктивна перевірка bcrypt (однаковий час відповіді).
- Пароль: ≥ 10 символів, ≤ 72 байти UTF-8, не збігається з логіном. bcrypt, cost 12.
- Access JWT (HS256, 15 хв) містить лише `sub` і `sid` — у пам'яті клієнта. На кожному запиті сервер завантажує з БД **користувача й сесію**: деактивація, зміна прав, logout і скидання пароля діють миттєво.
- Refresh — випадковий 32-байтовий токен (не JWT), у БД лише SHA-256 хеш; httpOnly, `SameSite=Strict`, `Secure` у продакшені, `path=/api/v1/auth`. Сесія ковзна: 12 год без активності.
- Ротація при кожному `/refresh`. Повторне використання вже ротованого токена пізніше ніж через 30 с → відкликаються всі сесії користувача + `SESSION_REUSE_DETECTED`. У межах 30 с (дві вкладки одночасно) — лише 401 без відкликання.
- Тимчасовий пароль (14 символів, без схожих символів) генерує сервер при створенні та скиданні; показується один раз. Поки `mustChangePassword`, усі приватні API повертають 403 `PASSWORD_CHANGE_REQUIRED`.
- Зміна пароля відкликає всі інші сесії, поточна лишається. Скидання пароля й деактивація відкликають усі.
- Першого адміністратора створює `scripts/seed.ts` із даними з env.
- Адміністратор не може деактивувати себе чи змінити власну роль. Оскільки змінювати користувачів може лише активний адміністратор, це гарантує, що щонайменше один активний адміністратор лишається завжди (окрема перевірка «останнього адміністратора» не потрібна).

### 6.4 Одночасне редагування однієї заяви

Клієнт надсилає `version`, яку бачив. Сервер виконує `updateOne({ _id, version }, { …, $inc: { version: 1 } })`. Якщо змінено 0 документів, повертається 409 «Заяву змінив інший користувач — оновіть сторінку».

## 7. Потенційні проблеми та ризики

1. **Транзакції потребують replica set.** На звичайному окремому `mongod` сервер не стартує, і це зроблено свідомо. → Локально запускаємо replica set з одного вузла або Atlas.
2. **Номер «наперед».** Будь-який ручний номер дозволено, тож помилково введений `9999т/26` назавжди займе номер. Автонумерація його пропустить і дубліката не буде. → Виправляється зміною номера або анулюванням. В UI — лише підказка «наступний автоматичний номер: N».
3. **Часовий пояс.** Якщо брати дату сервера в UTC, у першу годину-дві після опівночі 1 січня заява отримала б номер минулого року. → Дата й рік обчислюються строго за `Europe/Kyiv`.
4. **Дата як Date у MongoDB.** У MongoDB немає типу «дата без часу». → Єдина домовленість: опівніч UTC відповідної календарної дати, перетворення в одному модулі `kyivDate`. Фільтр періоду — `[from, to + 1 день)`.
5. **Двозначний рік.** `1т/26` → 2026. Номери до 2000 року неможливі (`99` → 2099). Для реєстру підприємства це прийнятно.
6. **Телефон.** Вважаю, що номери українські. Приймаю `0671234567`, `+38 (067) 123-45-67` тощо й нормалізую до `+380671234567`. Якщо бувають іноземні або стаціонарні з внутрішнім номером, правило треба послабити.
7. **Деактивований користувач** має заяви. → Лише `isActive: false`, ім'я лишається в реєстрі.
8. **Обсяг даних** → серверна пагінація, сортування й фільтрація, індекси під основні запити.
9. **Персональні дані** (ПІБ, телефони, email). Тіла запитів не логуємо, у журнал аудиту телефон і email не потрапляють.

### 10.2 Розгортання

1. Оновити код і залежності, зібрати (`npm run build`).
2. `npm run db:migrate -w server` — заповнює зведення `processing` у наявних заявах (ідемпотентно; повторний запуск також виправляє розбіжності).
3. `npm run db:indexes -w server` — створює нові індекси (колекції `engineers`, `calendarDays`, `applicationResponses`, `technicalConditions` і сортування реєстру за датами документів). У продакшені `autoIndex` вимкнено, тож без цього кроку їх не буде; локально Mongoose створює їх сам при старті сервера.
4. За потреби вказати `PROCESSING_START_DATE=YYYY-MM-DD` у `server/.env`: заяви, зареєстровані раніше, не показуватимуть попереджень про прострочення.
5. Адміністратор: «Налаштування → Інженери» — інженери кожного управління; «Налаштування → Календар» — свята, додаткові вихідні й робочі суботи.
6. Резервна копія: база й тека `UPLOADS_DIR` (скани відповідей і ТУ — разом зі сканами заяв, включно з попередніми версіями).

### 10.3 Залишкові питання

- Межа витрат газу — 100 000 м³/год (`GAS_FLOW_MAX`), припущення; змінюється однією константою.
- Сортування реєстру за номерами документів, інженером і витратами газу — без індексу (§5.7); при зростанні обсягу — додати індекси.
- Перелік станів розширюється в `PROCESSING_STAGES` і `stageOf()`; кожен новий стан треба додати до фільтра реєстру й назв (`labels.ts`).
