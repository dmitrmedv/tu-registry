# Authentication & Authorization

Фактична схема цього проєкту. Подробиці й причини — `docs/ARCHITECTURE.md` §6.3; код — `server/src/modules/auth`, `server/src/middlewares/authenticate.ts`, клієнт — `client/src/shared/api` (`http.ts`, `tokenStore.ts`). Зміна схеми — лише за погодженням.

| Елемент | Рішення |
|---|---|
| Вхід | логін + пароль; самореєстрації немає — акаунти створює адміністратор |
| Пароль | bcrypt (`BCRYPT_COST`, за замовчуванням 12); ≥ 10 символів, ≤ 72 байти UTF-8, не збігається з логіном |
| Access token | JWT HS256, 15 хв, містить **лише** `sub` і `sid`; на клієнті — тільки в пам'яті (`tokenStore`), ніколи не в localStorage |
| Refresh | випадкові 32 байти (не JWT); у БД — лише SHA-256 хеш (`refreshSessions`); httpOnly, `SameSite=Strict`, `Secure` у продакшені, `path=/api/v1/auth`; ковзна сесія 12 год |
| Ротація | кожен `/refresh` видає новий токен; повторне використання ротованого пізніше ніж за 30 с → відкликання всіх сесій + `SESSION_REUSE_DETECTED` |
| Тимчасовий пароль | генерує сервер при створенні й скиданні; поки `mustChangePassword`, приватні API повертають 403 `PASSWORD_CHANGE_REQUIRED` |
| Rate limit | 10 невдалих входів / 15 хв на пару IP + логін; однакове повідомлення «Невірний логін або пароль» |

## Перевірка доступу на сервері

- `authenticate` перевіряє access JWT і **завантажує користувача й сесію з БД** на кожному запиті: роль, `canManageRegistration`, `department`, `isActive`. Роль і права з JWT чи payload не беруться — тому деактивація, зміна прав і logout діють миттєво.
- Приватні маршрути — `requireAuth` (= `authenticate` + перевірка зміни пароля), ролі — `requireRole('ADMIN')`. Окремої схеми авторизації не вигадуй.
- Роль ≠ доступ до даних: доступ до заяв — за управлінням у сервісі (`application.access.ts`, див. skill `business-domain`); відмова пишеться в аудит як `ACCESS_DENIED`.
- Зміна пароля відкликає інші сесії; скидання пароля й деактивація — усі. Адміністратор не може деактивувати себе чи змінити власну роль.

## Frontend

- Один спільний refresh-проміс в інтерсепторі `http`: кілька одночасних 401 → один `/auth/refresh`.
- При старті застосунку — `POST /auth/refresh`; успіх означає, що користувач залогінений.
- Після logout — `queryClient.clear()`, щоб дані попереднього користувача не лишились у кеші.
- Приховування кнопок за роллю — лише UX; доступ завжди перевіряє сервер.

## Обов'язкові тести

login (успіх, невірний пароль → 401, rate limit), доступ без токена й з простроченим → 401, `PASSWORD_CHANGE_REQUIRED` → 403, refresh (успіх, ротація, повторне використання → відкликання всіх сесій), деактивований користувач → 401 одразу, недостатня роль → 403, `passwordHash` відсутній у відповідях.
