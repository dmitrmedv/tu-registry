# Бізнес-домен: реєстр заяв на технічні умови

Стислий перелік інваріантів. Подробиці й історія рішень — `docs/ARCHITECTURE.md` (§0 — рішення з номерами, §3 — колекції, §5 — нумерація і стани, §6 — доступ). Читай лише потрібний розділ.

**Джерело істини — код.** Якщо `ARCHITECTURE.md` розходиться з кодом, наслідуй код і повідом про розбіжність.

## Сутності

| Сутність | Колекція / код | Суть |
|---|---|---|
| Заява | `applications`, `modules/applications` | реєстраційний запис замовника; `status`: `ACTIVE` / `ANNULLED` |
| Управління | `departments` | має назву й код; код входить у номер заяви |
| Інженер | `engineers` | виконавець документів, прив'язаний до управління назавжди |
| Відповідь | `applicationResponses` | лист замовнику, коли ТУ одразу не підготувати; їх може бути кілька |
| Технічні умови (ТУ) | `technicalConditions` | **одні чинні** на заяву |
| Оплата за ТУ | `tuPayments` | **одна** на ТУ: рахунок → оплата → акт; може містити договір на оплату |
| Договір | `contracts` | договір на приєднання за чинними ТУ; їх може бути кілька |
| Проєкт | `projects` | узгодження проєкту за чинними ТУ; **один чинний** на заяву |
| Кошторис | `estimates` | кошторис чинного проєкту; **один чинний** на проєкт, перераховані лишаються |
| Рахунок | `invoices` | рахунок на приєднання за чинним проєктом; **кілька** (по одному на чергу будівництва) |
| Календар | `calendarDays` | винятки з правила «сб/нд — вихідні» |
| Історія змін | `applicationChanges` | зміни заяви та її документів по полях |
| Аудит | `auditLogs` | дії користувачів (`AUDIT_ACTIONS`); API на зміну журналу немає |

Enum-и й назви — `packages/shared/src/enums.ts` і `labels.ts`. Нове значення додавай туди, а не дублюй.

## Номер заяви

- Формат `Nт/РР-К` (`15т/26-8`), де К — **код управління**. Зберігається як `department` + `regYear` + `regSeq`; відображення — `formatRegNumber()`, розбір — `parseRegNumber()` / `parseRegNumberSearch()` у shared.
- Нумерація окрема для кожного управління й року; з 01.01 (за Києвом) починається з 1.
- Зміна коду управління змінює відображення номерів усіх його заяв (у заяві зберігається ідентифікатор управління, а не код).
- Сортування за номером — за числами, а не за рядком.

### Автоматична реєстрація
- Номер видає **лише сервер**: `$inc` на лічильнику `${year}:${department}` у транзакції (`modules/numbering`). Номери, зайняті вручну, пропускаються.
- Від дублікатів остаточно захищає unique-індекс `{ department, regYear, regSeq }`. Не замінюй цю схему на `count()+1` / `max+1`.
- Дата реєстрації — сьогодні за `Europe/Kyiv`.

### Ручна реєстрація й зміна номера чи дати
- Право мають лише `ADMIN` або користувач із `canManageRegistration`, і лише в заявах свого управління.
- Дата будь-яка в минулому, але **не в майбутньому**. Рік номера має збігатися з роком дати, номер має бути вільним, інакше 409.
- Лічильник не змінюється. Звільнений номер автоматика повторно не видає, його можна зайняти лише вручну.
- Пишуться `REG_NUMBER_CHANGED` / `REG_DATE_CHANGED` та історія old → new.

## Життєвий цикл заяви

- **Анулювання** замість видалення: обов'язкова причина, номер лишається зайнятим. Відновлює лише адміністратор.
- На анульованій заяві документи й скани не створюються й не змінюються (409).
- **Видалення назавжди** — лише адміністратор. Разом із заявою в одній транзакції видаляються її історія та документи, файли — після коміту. В аудиті лишається `APPLICATION_DELETED` з номером і датою, без даних замовника. Номер стає вільним для ручного внесення.
- **Оптимістичне блокування**: клієнт надсилає `version`; застаріла версія → 409. Зміни документів не змінюють `version` заяви.
- Обов'язкові поля нової заяви: замовник, телефон, населений пункт, місцевість, адреса, тип і категорія об'єкта, вид газифікації. У старих записах частини полів немає, тому в Mongoose вони не `required`; форма редагування просить їх заповнити.
- `objectCategoryOther` — лише для `OTHER`. `accountNumber` — лише для `RECONSTRUCTION`: в інших випадках сервер ці поля прибирає.

## Документи опрацювання

Спільна логіка — `server/src/modules/documents` (`DocumentKind`, `changeDocuments()`). Новий вид документа описуй через `DocumentKind`, а не окремою копією логіки.

- Дати документів — не раніше дати реєстрації заяви й не в майбутньому (за Києвом). Виняток — місяць передачі акта, який може бути майбутнім.
- Інженер — активний, з управління заяви. ПІБ зберігається знімком; уже обраного деактивованого можна лишити.
- Відповіді й ТУ звичайний користувач **скасовує** з причиною, а не видаляє. Відновлює й видаляє назавжди лише адміністратор.
- **ТУ:** одні чинні на заяву (частковий unique-індекс за `active: true`). Нові ТУ або відновлення, коли є інші чинні, → 409 `DOCUMENT_TAKEN`. Видалення ТУ видаляє і їхню оплату.
- **Оплата за ТУ:** суми в копійках (API — гривні). Змінювати можна лише оплату чинних ТУ активної заяви. Номер договору на оплату — окремий для управління, з 1, без скидання на рік, зберігається лише разом із датою договору.
- **Договір:** лише за чинними ТУ (інакше 409 `NO_TECHNICAL_CONDITIONS`). Номер `N-К` або `N-К-Р` для реконструкції; послідовність окрема для управління, без скидання на рік. Анулювання без відновлення. Стан заяви договір не змінює.
- **Проєкт:** лише за чинними ТУ (інакше 409 `NO_TECHNICAL_CONDITIONS`), один чинний (як ТУ). Проєктна організація обовʼязкова. Виконавець за замовчуванням — інженер чинних ТУ. Стан заяви проєкт не змінює.
- **Кошторис:** окремий документ (`estimates`) за чинним проєктом (інакше 409 `NO_PROJECT`): дата перевірки, сума й необовʼязкова сума по кошторису (субпідряд) (у копійках), скан (PDF), файл `.imd` (до 50 МБ, за розширенням). Перерахунок — новий кошторис, попередній «Перераховано» з файлами; проєкт не переузгоджується. Змінюють лише чинний кошторис чинного проєкту.
- **Рахунок:** лише за чинним проєктом (інакше 409 `NO_PROJECT`); кілька на заяву, кожен — основа своєї додаткової угоди. № вручну, необовʼязковий: його надає бухгалтерія згодом (до того — «б/н»); коментар — необовʼязковий; у новому рахунку за замовчуванням — 1, далі +1 до найбільшого числового № чинних рахунків. Дата не раніше узгодження проєкту; строк 10 робочих днів від узгодження лише показується (прострочення), не блокує. «До додаткової угоди №» — обовʼязкове, за замовчуванням наступний після чинних рахунків (перший — 1). Роботи — три списки, на початку порожні (назва + сума, ＋ «Додати роботу»): «БМР та врізання» (група за назвою; обрана «…за кошторисом» отримує суму чинного кошторису за замовчуванням), ПВР і «Дозволи на земляні роботи» (геодезія, дозвіл, інше) — лише коли точка приєднання ТУ — підземний газопровід. Загальна вартість = сума груп, у копійках. Біля дати одразу при введенні — «Кількість днів з дня узгодження — N»: зеленим у межах 10 робочих днів, червоним понад. Робочі дні рахунку — як NETWORKDAYS в Excel, обидва дні включно (той самий робочий день — 1). Файли: скан і підстава (PDF). Скасування з причиною; відновлення й видалення — адміністратор.
- **Скани:** PDF до 50 МБ, лише через `modules/scans`. Заміна скану відповіді чи ТУ зберігає попередній у `previousScans`. Скани не змінюють `version`.

## Стан, строки, хронологія

- Стан виводиться з документів у силі (`stageOf()` у `modules/processing/processing.summary.ts`):
  - є чинні ТУ → `TU_PREPARED`;
  - інакше остання відповідь з «Документи надійшли» → `IN_PROGRESS`;
  - остання відповідь без «Документи надійшли» → `RESPONDED`;
  - документів немає → `REGISTERED`.

  Анульована заява має власний `status`. Новий стан додавай у `PROCESSING_STAGES`, `stageOf()`, назви і фільтр реєстру.
- Зведення `applications.processing` перераховується **в тій самій транзакції**, що й зміна документа. Це кеш для реєстру, а не джерело істини.
- Строки рахує **лише сервер** у робочих днях від дати реєстрації: день реєстрації не рахується, день документа рахується. Норми: відповідь — 5 днів, ТУ — 10 (`RESPONSE_DEADLINE_DAYS`, `TU_DEADLINE_DAYS`). Робочий день визначає виняток календаря, а за його відсутності — правило «не сб/нд». Дати, які обирає користувач (документи, ручна реєстрація), — лише робочі дні: сервер відхиляє неробочий день, форма показує помилку одразу (2026-11-22). Зміна календаря одразу змінює всі розрахунки.
- Для заяв, зареєстрованих до `PROCESSING_START_DATE`, попередження «прострочено» не показуються.

## Доступ

- Користувач бачить і змінює **лише заяви свого управління**. Чужа заява для нього — 404, а не 403. Адміністратор має доступ до всіх.
- Реєструвати в інше управління й переносити заяву між управліннями може лише адміністратор. В архівне управління нічого нового не потрапляє.
- Довідники (управління, інженери, календар), користувачі й журнал аудиту — лише адміністратор.
- Права читаються з БД на кожному запиті. Відмова пишеться в аудит як `ACCESS_DENIED`. Приховування кнопок на фронтенді — лише зручність.

## Історія змін і аудит

- Кожна зміна заяви або її документа пишеться в `applicationChanges` (для документів — з `document: { kind, id, number }`) і в `auditLogs` одним викликом (`auditDocument` / `auditPayment` → `recordDocumentChange`).
- **Дані замовника** (телефон, email, особовий рахунок, коментар, замовник/адреса за ТУ, представник) потрапляють в історію змін зі значеннями, а в аудит — щонайбільше назвою поля, **без значень**.
- Скани в історії й аудиті позначаються лише як «файл», без імен файлів. Паролі й токени в аудит не потрапляють ніколи.
- Новий модуль картки додає свій вид у `HISTORY_DOCUMENT_KINDS` і дії в `AUDIT_ACTIONS`. Покриття для всіх модулів перевіряє `application.history.test.ts`.

## Дати

Календарні дати бізнес-логіки зберігаються як опівніч UTC відповідної київської дати. «Сьогодні» визначай лише через наявні утиліти (`kyivToday()` у `server/src/utils/kyivDate.ts`, `clock.now()`, `kyivCalendarDate()` у shared), а не через `new Date()` в UTC.
