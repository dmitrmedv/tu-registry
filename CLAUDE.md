# CLAUDE.md — постійні правила проєкту

## Мета

Працюй як уважний full-stack розробник. Реалізуй лише запитаний обсяг, зберігай наявну архітектуру та бізнес-правила. Не роби широкого аудиту репозиторію для локального завдання.

## Контекст репозиторію

Це внутрішній реєстр заяв на отримання технічних умов для приєднання до газових мереж.

- Архітектурні рішення й історія погоджень: `docs/ARCHITECTURE.md`.
- Предметні правила та критичні інваріанти: Skill `business-domain`.

Не вважай типовий шаблон із прикладів у Skills важливішим за фактичну реалізацію цього репозиторію. Перед зміною знайди аналогічну реалізацію та наслідуй її.

## Економне використання контексту

1. Починай із запитаного модуля та конкретних файлів. Не читай увесь репозиторій, `docs/ARCHITECTURE.md` чи всі Skills.
2. Спершу використовуй `Glob`/`Grep` для пошуку точок входу, потім читай лише потрібні фрагменти й пов'язані файли.
3. Не відкривай `node_modules`, `.git`, `dist`, `coverage`, `uploads`, `playwright-report`, `test-results` та `.env`. Для змінних середовища використовуй `.env.example`.
4. Не виводь великі файли цілком, якщо достатньо пошуку символу або конкретного діапазону.
5. Не повторюй у відповіді вміст файлів чи довгі плани. Звітуй стисло: що змінилося, які перевірки реально запущено, що залишилось.
6. Не запускай паралельних агентів для простих локальних завдань. Subagent використовуй лише для незалежного аналізу або окремого review.

## Обов'язкові правила реалізації

- Мінімальний diff: не роби незапитаного рефакторингу, перейменувань або форматування всього проєкту.
- Перед створенням компонента, хука, утиліти чи сервісу знайди наявний аналог. Не дублюй логіку.
- Зберігай доменне розділення й поточні шари. Backend: `routes → controller → service → model`.
- Сервер — джерело істини для валідації, прав доступу та бізнес-правил.
- Не додавай npm-залежності, колекції, індекси, API-контракти чи нові абстракції без обґрунтування; значущі архітектурні зміни погоджуй.
- Не послаблюй і не видаляй тести, щоб приховати помилку.
- Не вигадуй результати lint, typecheck, тестів або build. Повідомляй тільки фактично запущені команди й результати.
- Не коміть і не пуш без прямого прохання.

## Критичні технічні домовленості

- Поточний користувач і його права завантажуються з БД; не довіряй ролі чи дозволам із клієнтського payload/JWT.
- Дати бізнес-логіки — часовий пояс `Europe/Kyiv`; використовуй наявні `kyivToday()` / `clock.now()`.
- Не зберігай access token у localStorage.
- Домовленості лише для серверу чи клієнта — у `server/CLAUDE.md` і `client/CLAUDE.md`.

## Перевірки

Запускай найменший достатній набір для зміненого коду, а перед завершенням етапу — повний набір скриптів із кореневого `package.json` (`lint`, `typecheck`, `test`, `test:e2e`, `build`), якщо середовище дозволяє.

E2E потрібні для змін ключових користувацьких сценаріїв. Не запускай повний E2E після суто текстової чи ізольованої стилістичної зміни.

## Навігація Skills

Завантажуй Skill лише коли він відповідає поточній задачі; `project-architect` — лише для великих нових функцій або архітектурних рішень.

## Формат звіту

Коротко вкажи:
1. Що зроблено.
2. Які файли змінено.
3. Які команди реально запущено та їх результат.
4. Відомі обмеження або наступний крок.
